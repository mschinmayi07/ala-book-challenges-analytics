# Phase 2: MySQL

[Back to the main README](../README.md)

Phase 2 takes the four clean tables from Phase 1 and puts them into a **MySQL database**
(`banned_books_db`). It then answers 10 business questions about book challenges with SQL.
The database is also ready to be connected to **Power BI** in Phase 3.

Phase 2 has three parts:

1. **A schema** (`sql/schema.sql`): the table definitions, keys and indexes.
2. **A loader** (`scripts/load_to_mysql.py`): a Python script that builds the database and fills it from the CSVs.
3. **Queries** (`sql/queries.sql`): the 10 analysis questions, written in SQL.

## 2. The database design

It is the same **star schema** as Phase 1: one fact table, one dimension table and two bridge
tables. A **bridge table** is needed here because the relationship is **many-to-many**: one case
can challenge many titles, and one title can be challenged in many cases.

```
                    dim_title
                  (PK row_index)
                        ^
                        |  row_index  (nullable, ON DELETE SET NULL)
                        |
fact_case  <------ bridge_case_title
(PK case_id)    case_id  (ON DELETE CASCADE)
    ^
    |  case_id  (ON DELETE CASCADE)
    |
bridge_case_reason
(PK case_id + reason)

fact_case_deduped  = VIEW on fact_case without probable duplicates
```

### The four tables

| Table | Rows | Primary key | What one row is |
|---|---|---|---|
| `dim_title` | 10,380 | `row_index` | One book (or other item), with Google Books details such as summary, maturity rating and page count |
| `fact_case` | 5,373 | `case_id` | One challenge case: year, state, who started it, and counts of what happened |
| `bridge_case_title` | 41,381 | `bridge_id` (surrogate, `AUTO_INCREMENT`) | One title inside one case, with its outcome |
| `bridge_case_reason` | 7,050 | `case_id` + `reason` (composite) | One reason given in one case |

### Foreign keys

| Child column | Parent column | Rule | Why |
|---|---|---|---|
| `bridge_case_title.case_id` | `fact_case.case_id` | `ON DELETE CASCADE` | If a case is deleted, its title rows go too |
| `bridge_case_title.row_index` | `dim_title.row_index` | `ON DELETE SET NULL` | If a title is deleted, the bridge row stays but loses its title link. The column is nullable on purpose |
| `bridge_case_reason.case_id` | `fact_case.case_id` | `ON DELETE CASCADE` | If a case is deleted, its reasons go too |

Two columns are **deliberately not** foreign keys:

- `bridge_case_title.candidate_row_index` is only a "best guess for review". It is not a real relationship.
- `fact_case.probable_duplicate_of_case_id` is just a flag that points to another case.

### Indexes

| Index | Column | Why |
|---|---|---|
| `idx_fact_case_year` | `fact_case.year` | Many queries group or filter by year |
| `idx_fact_case_state` | `fact_case.state` | Per-state totals |
| `idx_bridge_case_title_row` | `bridge_case_title.row_index` | The most common join (bridge to title) |

InnoDB already creates an index for every foreign key. For `row_index` it replaces its automatic
index with the explicit one, so there is no duplicate.

### Column types (chosen after reading the real CSVs)

| Kind of data | MySQL type | Notes |
|---|---|---|
| IDs, years, counts | `INT` | |
| Short labels (state, outcome, initiator) | `VARCHAR(n)` | `n` is sized from the longest value seen, with room to spare |
| Long free text (`summary`) | `TEXT` | Longest summary in the original data was 4,687 characters. This repo's copy holds only the placeholder `NOT_FOUND` |
| Confidence scores (0-100) | `DECIMAL(5,2)` | Exact, no floating-point rounding |
| Flags (`is_book`, `needs_manual_review`, ...) | `BOOLEAN` | Stored as 0/1. The CSVs use `True`/`False` or `0`/`1`; the loader converts both |
| Every text column | `utf8mb4` | Needed for names like Sáenz, Ramée, Bernières |

Columns with **zero** empty cells in the CSVs are `NOT NULL`. Columns that have real gaps stay nullable.

## 3. What I found when I checked the CSVs

Before writing the schema I checked the files and, names, row counts and primary keys all matched, but, these things did not:

| Finding | What the schema/loader does |
|---|---|
| `dim_title.year` has 15 corrupt values (e.g. 202, 20224, 2003202) | Loaded as-is. Not fixed in SQL |
| `dim_title.page_count` contains the text `NOT_FOUND` on 511 rows | Loader stores `NULL`, so the column can be `INT`. The loader prints the count |
| `dim_title.isbn` is up to 616 characters. Some rows list several ISBNs, and one holds a pasted "Subjects:" block | `VARCHAR(700)` |
| `raw_title_string` is at most 223 characters (plan said `TEXT`) | `VARCHAR(300)`: enough, and easier to index and group |
| `adversarial_group_involvement` is up to 435 characters | `VARCHAR(500)` |
| `fact_case.state` has the code `INT` (international) and 4 empty values | Loaded as-is |
| 7 cases have `NULL` in every count column: the 4 corrupted cases plus cases 419, 1036 and 1567 | Loaded as-is. Aggregates skip `NULL` |
| `dim_title` uses `NOT_FOUND` as a word in `maturity_rating`, `language` and `summary` | Kept as text. Filter it out when needed. In this repo `summary` is `NOT_FOUND` on every row (see the main README) |
| 4 summaries contain the replacement character ? | Comes from the source data. Loaded unchanged |
| Pandas would turn real text such as `None` or `NA` into `NULL` by default | Loader reads with `keep_default_na=False`, so only **empty** cells become `NULL` |

The loader was also checked end to end (on the original data, before the summaries were replaced for this repo): every `title`, `author`, `summary` and `isbn` value read back from MySQL was **byte-identical** to the CSV, accents included.

## 4. The 10 queries

Counting rule used throughout: "times challenged" means the number of rows in
`bridge_case_title` (one row per title per case). Only rows with a `row_index` can be joined to
`dim_title`, so non-book rows and unmatched titles drop out of the title-based queries.

| # | Question | Main techniques |
|---|---|---|
| 1a | Top 15 most-challenged titles | `INNER JOIN`, `GROUP BY`, `COUNT`, `ORDER BY`, `LIMIT` |
| 1b | Top 15 most-challenged authors | same, with `IS NOT NULL` |
| 2 | Year-over-year % change in titles challenged | CTE, `SUM`, `LAG() OVER`, `NULLIF`, `CAST` |
| 3 | Most-challenged title in each year | two CTEs, `RANK() OVER (PARTITION BY year ...)`, filter on rank 1 |
| 4 | Reasons given, by year | join, `GROUP BY year, reason` |
| 5a | Initiator vs. outcome | join, `GROUP BY initiator, outcome`, `COALESCE` |
| 5b | Retained-rate per initiator | `SUM(CASE WHEN ...)` divided by `COUNT(*)`, `CAST` |
| 6 | Fiction vs. non-fiction share per year | CTE, `SUM(...) OVER (PARTITION BY year)` |
| 7 | Books rated `MATURE` but shelved for `Children` | `LEFT JOIN`, `WHERE` filter, `COUNT` |
| 8 | Titles challenged per state + running total | CTE, `SUM(...) OVER (... ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW)` |
| 9a / 9b | Rows needing manual review, grouped / listed | `WHERE needs_manual_review = TRUE`, `GROUP BY match_method` |
| 10 | Cases on the target list vs. not | `AVG`, `SUM`, removal rate with `NULLIF` |

## 5. Changes and additions made after the first delivery

After the first version, these were changed or added. They are also listed in `sql/CHANGELOG.md`.

### 5.1 New view: `fact_case_deduped` (in `schema.sql`)

```sql
CREATE VIEW fact_case_deduped AS
SELECT * FROM fact_case
WHERE probable_duplicate_of_case_id IS NULL;
```

- **Why:** case `4564` is flagged as a probable duplicate of case `3939` and may double-count 2023.
  The view hides it so queries can use "deduplicated" cases without repeating the filter.
- **Size:** 5,372 rows (5,373 minus case 4564).
- **Re-runnable:** a `DROP VIEW IF EXISTS fact_case_deduped;` was added as the first statement,
  and the view is created last, after the tables.
- **Watch out:** the view uses `SELECT *`, so if columns are ever added to `fact_case`, re-run
  `schema.sql` to refresh it.

### 5.2 Queries now read the view (in `queries.sql`)

| Query | Change | Effect on the results |
|---|---|---|
| 1a, 1b | `INNER JOIN fact_case_deduped` added | Counts drop slightly (e.g. *All Boys Aren't Blue* 309 to 308, *The Bluest Eye* 247 to 246) |
| 3 | uses `fact_case_deduped` | None: same winners |
| 5a, 5b | uses `fact_case_deduped` | Small shifts. Missing-initiator + unknown-outcome rows go from 3,374 to 2,636 |
| 6 | uses `fact_case_deduped` | Small shifts in counts and percentages |
| 7 | second `LEFT JOIN` to the view, and `COUNT(b.bridge_id)` became `COUNT(c.case_id)` | None today. A title still shows with 0 if all its challenges were in excluded cases |
| 9a, 9b | `INNER JOIN fact_case_deduped`; columns written as `b.column` | None: no review row belongs to case 4564 |
| 10 | `FROM fact_case_deduped` | None: case 4564 already had a `NULL` flag |
| 2, 4, 8 | **unchanged**, still read `fact_case` | Case 4564 cannot affect them (see below) |

In total the view removes **738** `bridge_case_title` rows, all belonging to case 4564.

**An important finding about case 4564.** Cases 3939 and 4564 are both corrupted rows with a
`NULL` `count_titles_challenged`. So they add **nothing** to the `SUM` in queries 2 and 8, and
4564 has no reason rows for query 4. The duplicate problem only appeared in queries that count
`bridge_case_title` rows (3939 has 731 bridge rows, 4564 has 738). That is why those are the
ones now using the view.

### 5.3 New file: `sql/row_count.sql`

One query using `UNION ALL` that returns the row count of each of the four tables. It counts the
base tables, so `fact_case` shows 5,373, not the view's 5,372.

## 6. Results at a glance

(From the exported CSVs, with case 4564 excluded where the view is used.)

- **Most challenged title:** *Gender Queer: A Memoir* (464), then *All Boys Aren't Blue* (308) and *The Bluest Eye* (246).
- **Most challenged authors:** Ellen Hopkins (1,350) and Sarah J. Maas (1,164) lead, then Maia Kobabe (467).
- **Top title each year:** 2016 *This One Summer*, 2017 *Thirteen Reasons Why*, 2018-2020 *Melissa*, 2021-2024 *Gender Queer*, 2025 *SOLD*.
- **Trend:** titles challenged rise from 260 (2016) to 3,249 (2021, +1,028%), 7,598 (2022), 10,032 (2023), then 6,175 (2024) and 8,434 (2025).
- **Reasons:** over all years, "Content Considered Sexually Explicit" (1,902) and "LGBTQIA+ Representation" (1,889) are far ahead of the rest. The biggest single cell is LGBTQIA+ Representation in 2022 (580 cases).
- **Retained-rate:** Patrons are highest (28.1% of all rows, 72.8% of known outcomes). Government (0.2%) and Administrators (1.6%) are lowest.
- **States:** Florida (7,656) and Texas (6,755) lead the totals.
- **Target list:** cases on the target list average 10.9 titles and a 40.1% removal rate. Cases off it average 1.3 titles and 17.6%.
- **Mature but shelved for children:** 17 titles, led by *It's Perfectly Normal* (128 challenges).
- **Review queue:** 61 rows need manual review (31 `unmatched`, 30 `fuzzy`).

## 7. Known limitations

- **The 2021 jump (+1,028%) is probably partly a data-collection effect,** not only more challenges. Check this before drawing conclusions.
- **About half of `bridge_case_title` rows have outcome `unknown`.** Outcome-based rates (queries 5a, 5b) depend heavily on how you treat them.
- **Elected Officials and cases with missing initiators** look like ~50% on the known-outcome rate but 3.1% and 2.4% on the all-rows rate. Most of their rows are `unknown`.
- **Title-based queries skip non-book items and unmatched titles** (774 bridge rows have no `row_index`).
- **Query 8 contains a `NULL` state group** (4 corrupted cases) and an `INT` group.
- **`dim_title.year` has 15 corrupt values** and `NOT_FOUND` appears as text in a few columns. Filter these before analyzing publication years or Google Books fields.
- **Text comparisons ignore case and accents** (the collation).
- **Duplicate case 4564 is excluded only where the view is used.** Whether it is truly a duplicate is a judgment call; to include it again, change `fact_case_deduped` back to `fact_case` in that query.

## Key terms used in this project

| Term | Meaning |
|---|---|
| **Star schema** | A fact table in the middle, linked to dimension tables around it |
| **Fact table** | One row per event (here, one challenge case) |
| **Dimension table** | Descriptive details (here, the titles) |
| **Bridge table** | A table that connects two tables in a many-to-many relationship |
| **Primary key (PK)** | A column (or columns) that uniquely identifies each row |
| **Surrogate key** | An artificial ID with no meaning of its own (`bridge_id`) |
| **Composite key** | A primary key made of two columns (`case_id` + `reason`) |
| **Foreign key (FK)** | A column that points to a primary key in another table |
| **`ON DELETE CASCADE`** | Deleting the parent row also deletes the child rows |
| **`ON DELETE SET NULL`** | Deleting the parent row blanks the link in the child rows |
| **Index** | A lookup structure that makes filtering and joining faster |
| **View** | A saved query that behaves like a table |
| **CTE** | `WITH ... AS (...)`: a named, temporary result used inside one query |
| **Window function** | A calculation across related rows without collapsing them (`LAG`, `RANK`, `SUM() OVER`) |
| **Collation** | The rules for comparing and sorting text |
| **utf8mb4** | A character set that stores all Unicode characters, including accents |
| **Idempotent** | Safe to run many times with the same result |
| **Sentinel value** | A placeholder word standing in for missing data (`NOT_FOUND`) |
